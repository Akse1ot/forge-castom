# Forge Custom Set Builder — 1.0

Этот навык обслуживает **локальный MTG Forge пользователя**. Прочитай применимый `AGENTS.md`, затем используй настоящий текущий код Forge и материалы навыка. Полная договорённость — в `SPECIFICATION.md`, но не загружай её без необходимости: ниже рабочий алгоритм. Вспомогательные файлы `references/` читай **по конкретной потребности**, а не все подряд.

## Границы и приоритеты

- **Правильная реализация важнее экономии, экономия важнее избыточного контроля.** Изучай исходники настолько глубоко, насколько нужно для понимания; полный класс/цепочку вызовов читать разрешено. Повторно используй уже подтверждённые знания, но не считай их вечной истиной: Forge меняется.
- В **локальный Forge** разрешено вносить **только Java-изменения, отдельно одобренные пользователем на этапе 5**, и минимально необходимые для них тесты. Не делать Git push/pull, reset/clean или синхронизацию с удалённым репозиторием. Перед Java-правками проверь `git status` и возможность локального отката; сохраняй чужие правки. Не коммить автоматически.
- Все **скрипты карт, tokenscripts, изображения, editions и связанные результаты** создавай **только в отдельной рабочей папке вне каталогов игры/исходников Forge**. Даже готовые не устанавливай: пользователь переносит их вручную.
- Нельзя молча упрощать текст, выдумывать синтаксис/эффекты, считать успешную загрузку полноценным игровым тестом. Честно помечай частичные/заблокированные карты.
- Не выполняй отдельный мониторинг upstream Forge, глобальный аудит пользовательских Java-патчей, оценку силы Draft AI, самостоятельную балансировку бустеров или генерацию отсутствующих иллюстраций. Это другие задачи.
- Никаких повторных полных аудитов, компиляций и тестов без технической причины. Приоритет — минимально достаточное подтверждение реальной корректности.

## Вход и подготовка

Получить от пользователя URL выпуска, вид (`draft classic`, `draft custom`, `non-draft`), **точно заданную схему бустера для драфтового выпуска**, если есть, путь Forge и место результатов. Если драфтовая схема неполна, не придумывать её: отметить блокер для согласования. При наличии уже начатого проекта **продолжать его** с прежним кодом и утверждёнными решениями.

Рекомендуемый каталог результата: `D:\1\forge-builder\<CODE>\` с подпапками `cards`, `tokens`, `editions`, `images`, `source`, `reports`, файлами `INSTALL.md` и при длительных перерывах `progress.md`. Только пример; заданный пользователем путь главнее. Временные данные не копировать в папку навыка.

**Код:** уникальный вариант из **ровно четырёх латинских A–Z**, образованный из названия. Проверить все локальные `Code=` в `forge-gui/res/editions`, включая кастомные, без учёта регистра. При конфликте автоматически пробовать другие осмысленные сочетания (`TEOW` → `TEXW`, `EXOW`), не менять существующие и не запрашивать отдельного одобрения. Зафиксировать код в материалах выпуска и не менять после продолжения.

**Коллизии имён:** сверять `Name:` имеющихся карт и listings, а также имена текущего проекта (учесть Windows/casefold). Сохранять свободное оригинальное имя; занятому имени давать первый **свободный** суффикс через пробел `I`, `II`, `III`…; чужие карты не переименовывать. Пример: `Name:Brimstone Mage I`, `Brimstone_Mage_i.txt`, `1 R Brimstone Mage I`, `Brimstone Mage i.fullborder.jpg`. Завести стабильную карту `source_id/URL → original_name → forge_name` и применять её к ссылкам между картами, токенам, editions, изображениям; не переписывать Oracle механически. Дополнительные лица/варианты арта одной карты не считать автоматически новой картой с конфликтом имени. См. `references/names-and-identity.md`.

## Работа в шесть этапов

### 1. Импорт → классификация → скрипты A

Один раз извлечь максимально полный каталог: source IDs, все лица, исходные тексты, стоимости, типы, P/T, редкости, номера, изображения/токены. PlaneSculptors обычно содержит общий список текстов, MTGNexus — постраничный визуальный спойлер с переходом в каждую карту. Проверить полноту, пагинацию, дубли, неопределённые поля; сохранять локальный `source/cards.json` или прозрачный эквивалент. Смотреть `references/sources-and-images.md` и опционально запустить `scripts/check_manifest.py` для **нашего нормализованного формата** (он не является парсером сайта).

Классифицировать все карты:
- **A** — реализуемы имеющимся локальным движком (штатным или кастомно расширенным); можно сразу **пакетно написать скрипты в staging**.
- **B** — зависят от общей пока недостающей механики; группировать все варианты и пересечения.
- **C** — требуют индивидуального сложного скрипта или небольшого патча даже ради одной карты; разрабатывать индивидуальное решение.
- **D** — предварительно требуют **масштабной перестройки основ движка**; не пытаться реализовать, кратко вынести пользователю.

Неоднозначный/неполный оригинал — **отдельная пометка**, а не автоматическая D. На стандартных картах использовать известные скрипты и текущие операторы; без индивидуального глубокого тестирования каждой карты. См. `references/forge-scripting.md`, `references/ai-hints.md`.

### 2. Групповые механики B

Собрать **все** карты каждой механики, включая комбинированные; проверить актуальную встроенную и кастомную поддержку; глубоко изучить нужные Java-цепочки, если требуется. Один раз спроектировать общий интерфейс скриптов, минимальные hooks/helpers и адресные проверки. Сначала изолированное решение, не меняющее глобальную семантику. **Java пока не менять.** См. `references/engine-patches.md`.

### 3. Индивидуальные C, список D

Для C спроектировать точный скрипт либо локальный Java-патч; небольшие индивидуальные патчи **не запрещены**. Чрезмерное вмешательство → D, **без детальной разработки**. Дать причины и зависимости для каждого исключения.

### 4. Аудит планов и компактный отчёт

Без повторной проверки всех A: осмотреть планы B/C, возможные конфликты с текущим Java и друг с другом, неполные источники, возможные неполученные изображения/токены, параметры booster и список D. Дать короткий сводный план изменений с отдельными решениями, которые должен принять пользователь. См. `templates/decision-report.md`.

### 5. Обязательное согласование

**Остановиться перед Java-правками и доработкой B/C.** Получить решение пользователя по планам: утвердить/скорректировать/отклонить. Не заставлять утверждать каждую A. Существенное отступление от утверждённого плана снова вынести на решение.

### 6. Реализация, ресурсы, editions, проверка

Внести **только одобренные** Java-изменения непосредственно в локальный Forge. Скрипты B/C, токены, editions, изображения создавать **исключительно во внешней папке результата**. Массово проверить загрузку/ссылки, корректность явно заданных бустерных слотов, адресно проверить новые/рискованные механизмы. Оставить всё для **ручной** установки. См. `references/validation.md`, `references/editions.md` и `templates/delivery-report.md`.

**Нереализованные карты не исчезают:** сохранять номер и редкость, в `[cards]` поставить комментарий `# 103 R Example Card`, а в отчёте дать причину и статус. Не придумывать замену или подкладывать пустой скрипт; предупреждать, если из-за пропусков не хватает пула для заданных бустеров. Изображения скачивать полноразмерные по ссылке, не обрезанные previews; отдельно перечислять отсутствующие **карты / токены / эмблемы**. Ничего не рисовать автоматически.

## Качество, знания и продолжение

- Проверяй `SVar`, `TokenScript`, оба лица карты, реальный эффект, условия/цели, `may`/`up to`, `DeckHas` vs `DeckHints` vs `DeckNeeds`; семантику `&`/`|` подтвердить в локальном Forge. Без пустой первой строки и лишних пустых строк. В качестве **исторических уроков**, а не вечной нормы API, см. `references/dwap-lessons.md`.
- Не проводить все тесты на каждой карте: достаточно проверки структуры и массовой загрузки + **нескольких адресных сценариев** для новых или рискованных эффектов. `BUILD SUCCESS` не означает, что все карты функционально подтверждены. Ссылки на источник сохранять.
- Применяй знание из `references/knowledge-index.md` только после **быстрой релевантной проверки** классов/методов текущей ветки. При обнаружении изменений исследовать их в нужной глубине; не устраивать отдельный полный аудит upstream. Пополняй справочники **только повторно полезными и подтверждёнными** выводами, со статусом и контекстом. Не привязывать Skill к удаляемой временной папке.
- Для продолжения через новые сессии или дни сохраняй краткий `progress.md` по мере необходимости, а не после каждой карты. Повторно используйте локально сохранённые данные и готовые скрипты; не перечитывать сайт без причины.
- Перед завершением выдать фактические числа и статусы: что импортировано, готово, частично готово, заблокировано, не проверено; какие Java-файлы изменены по одобрению, какие изображения отсутствуют, как проверены бустеры, где файлы для ручной установки. Временные данные **не удалять без разрешения**.

**Первый запуск для формирования базы знаний по завершённым аудитам DWAP — `references/first-run.md`; это отдельная однократная процедура, не обычный запуск генерации.**
