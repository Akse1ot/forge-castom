# Forge Custom Set Builder — спецификация v1.0

**Статус:** согласованная спецификация v1.0 с правилом разрешения совпадающих имён карт. **Не является командой Codex на выполнение.**

## 1. Назначение и границы

Forge Custom Set Builder — специализированный рабочий процесс Codex для переноса кастомных выпусков Magic: The Gathering из PlaneSculptors, MTGNexus и, в перспективе, аналогичных источников в MTG Forge. Он извлекает исходные данные, разрабатывает скрипты и при необходимости планы небольших расширений движка, готовит токены, изображения и файл выпуска, выполняет разумные проверки и сообщает о проблемах.

**Итоговые скрипты, изображения и файлы выпуска всегда подготавливаются вне игровых каталогов; пользователь переносит их вручную.** Единственное разрешённое изменение основного локального Forge в рамках этого процесса — **предварительно согласованные Java-патчи** и минимально необходимые для них проверки. Синхронизация с удалённым Git и отдельная рабочая копия движка не требуются.

Не входят в задачу: мониторинг изменений оригинального Forge; аудит всех пользовательских доработок ядра; автоматическая установка карт в игру; автономное проектирование драфтового баланса; создание отсутствующих иллюстраций; гарантия идеальной игры ИИ.

## 2. Основные принципы

1. **Корректность прежде экономии, экономия прежде избыточной полноты.** Глубина исследования и тестирования должна соответствовать риску. Нельзя экономить ресурсы за счёт выдуманного синтаксиса, непонимания движка или молчаливого упрощения способностей.
2. **Текущие исходники Forge имеют приоритет.** База знаний помогает, но не заменяет проверку актуальных классов, операторов и цепочек выполнения. При необходимости Codex читает целые классы и связанные подсистемы.
3. **Использовать уже реализованное.** Сначала штатный API и проверенные кастомные расширения текущей локальной версии; затем обоснованное предложение нового механизма.
4. **Допускается патч даже ради одной карты.** Количество карт не определяет допустимость вмешательства. Codex разрабатывает план; решение об объёме и приемлемости вмешательства принимает пользователь.
5. **Не менять глобальную семантику ради частного случая**, если можно добавить изолированный селектор, помощник или минимальный локальный хук. Если такого решения нет, честно описать компромисс.
6. **Нет приблизительным реализациям без разрешения.** Частично реализованная карта никогда не выдаётся за готовую.
7. **Повторно использовать исследованное.** Анализировать общие механики один раз для всей группы; не перечитывать исходники и страницы без причины.
8. **Не загрязнять рабочее пространство.** Временные данные и результаты выпуска отделены от репозитория; постоянные знания навыка компактны и независимы от временных отчётов.

## 3. Исходные параметры задания

Пользователь сообщает ссылку на выпуск и режим подготовки: **драфтовый** либо **недрафтовый**. Для драфтового выпуска пользователь **сам задаёт состав бустера и особенности слотов** в первом задании. Codex не придумывает их и не балансирует драфт по своему усмотрению. Если параметры неполны или неосуществимы средствами Forge, Codex сообщает об этом в плане, не заменяя требования незаметно.

Опционально пользователь указывает имя/код выпуска, исключения, особенности токенов, условия сохранения изображений и другие ограничения. Если существующий проект того же выпуска уже ведётся, Codex продолжает его, сохраняя утверждённые решения и код.

## 4. Код и идентичность выпуска

При первичном импорте Codex предлагает **ровно четырёхбуквенный код A–Z** на основе названия: например, The Exploration of Whisperwild → `TEOW`. Он проверяет на совпадения значения `Code=` во всех доступных файлах `forge-gui/res/editions/` (включая стандартные и кастомные) без учёта регистра. Если сочетание занято другим выпуском, самостоятельно выбирает другое осмысленное четырёхбуквенное сочетание из названия (`TEXW`, `EXOW` и т. п.), пока не найдёт свободное. Переименовывать существующие выпуски нельзя; дополнительное согласование при обычном конфликте кодов не требуется.

Однажды выбранный код записывается в состояние конкретного проекта и **не пересчитывается при возобновлении**. Если код уже относится к этому же продолженному проекту, он сохраняется. Для действительно отдельного дополнения со своим файлом выпуска требуется отдельный уникальный код.

### 4.1. Уникальные имена карт в Forge

Кастомная карта может иметь то же имя, что официальная карта или другая уже добавленная кастомная карта. **Существующие карты не переименовывать**. Перед созданием скриптов Codex сверяет имена импортируемых карт с текущей базой Forge: прежде всего с `Name:` имеющихся скриптов и записями выпусков, а также с именами уже назначенных карт данного проекта. Сравнение учитывает возможные коллизии регистра и файловых имён в Windows. Проверку проводить не только по имени файла скрипта.

Если исходное имя свободно, оно сохраняется без суффикса. При совпадении новой карте автоматически присваивается свободный вариант с **римским числом через пробел**: `I`, `II`, `III`, `IV` и далее. Каждый кандидат тоже проверяется на совпадение, включая уже существующие имена с такими суффиксами. Переименование не требует отдельного согласования, но фиксируется в отчёте. При возобновлении проекта уже назначенное имя не пересчитывать.

**Единая схема для примера `Brimstone Mage` → `Brimstone Mage I`:**

```text
Скрипт:                 Brimstone_Mage_i.txt
Внутри скрипта:         Name:Brimstone Mage I
Строка в [cards]:       1 R Brimstone Mage I
Полное изображение:     Brimstone Mage i.fullborder.jpg
```

В отображаемом имени и кард-листе римская цифра пишется заглавными буквами; в имени скриптового файла и изображения — строчными по принятой пользователем схеме. Расширение и формат изображения сохранять совместимыми с фактически используемыми правилами Forge. Для многочастных карт, токенов и иных связанных ресурсов применять согласованное именование с учётом их реальных идентификаторов.

Хранить в материалах текущего выпуска **соответствие «исходное имя / присвоенное имя Forge»**, привязанное к конкретной записи источника, а не только к текстовому названию. Использовать его во всех скриптах, записях `editions`, изображениях и ссылках на конкретные карты. При необходимости корректировать явные обращения к переименованной карте в логике скрипта; **не переписывать Oracle и описания способностей механически** — проверять смысл и требования Forge. Нереализованная карта также получает своё зарезервированное имя и сохраняется в кард-листе закомментированной под этим именем.

## 5. Классификация карт

**A — реализуются текущим движком.** Включая штатные и уже имеющиеся в локальном Forge кастомные возможности. Скрипты можно создавать сразу на первом этапе во временной папке.

**B — зависят от общей новой механики.** Несколько карт или вариантов эффекта рассматриваются вместе. Разрабатывается единое решение и перечень зависимых карт; Java-патч пока только планируется.

**C — индивидуальные сложные карты.** Возможна нетривиальная комбинация существующих операторов или небольшой индивидуальный патч; факт, что патч нужен только одной карте, не препятствие.

**D — чрезмерная сложность вмешательства в основу движка.** Когда предварительная оценка указывает на масштабную перестройку фундаментальных систем, Codex **не пытается** реализовывать такую карту в обычном процессе. Он фиксирует её и краткую причину; решение о дальнейшей судьбе принимает пользователь.

Неполный, противоречивый или неясный оригинальный текст — **отдельная пометка «требует уточнения источника»**, а не повод автоматически относить карту к группе D. Карты могут зависеть более чем от одной общей механики; такие зависимости фиксируются.

## 6. Шесть этапов работы

### Этап 1. Импорт, первичный анализ и скрипты группы A

- Получить полный перечень карт, уникальные идентификаторы, названия и части карт, стоимость, типы, P/T, Oracle, редкости, номера, изображения и сведения о токенах, насколько они доступны.
- Один раз сохранить машиночитаемый снимок источника для дальнейших этапов. Проверить пропуски, дубли и многочастные карты; изображения использовать для уточнения только там, где текстовый источник неполон.
- Назначить свободный четырёхбуквенный код и разрешить конфликты имён карт с существующей базой Forge; закрепить исходные и присвоенные имена.
- Классифицировать карты A/B/C/D и отдельно отметить вопросы к оригиналу.
- Сразу создавать во временной папке скрипты группы A, пакетами удобного размера, по реальным аналогам Forge; не трогать игровые каталоги.
- Провести недорогие пакетные проверки структуры, ссылок на SVar и существования используемых токен-скриптов. Тяжёлые игровые тесты на этом этапе не нужны для каждой типовой карты.

### Этап 2. Общие новые механики (B)

- Сгруппировать все зависимые карты по механикам, выявить их варианты и пересечения.
- Исследовать соответствующие участки текущего движка в необходимой глубине; проверить существующие кастомные расширения.
- Спроектировать общий механизм, минимальные точки вмешательства, скриптовый интерфейс и несколько адресных сценариев проверки.
- **Не менять Java-код и не объявлять патч одобренным.** Явно отделить известное от предполагаемого.

### Этап 3. Индивидуальные карты (C) и список D

- Для C разработать по каждой карте работоспособную скриптовую схему или план локального патча. Патчи ради одной карты допустимы, если пользователь сочтёт вмешательство приемлемым.
- Если обнаруживается необходимость крупных архитектурных изменений, перевести карту в D без попытки перелопатить движок.
- Для D собрать краткий перечень причин и возможных направлений дальнейшего обсуждения **без детального проектирования**.

### Этап 4. Разумный аудит планов и сводный отчёт

- Проверить планы B/C на внутренние противоречия, совместимость с текущим Forge, перекрывающиеся патчи и риск изменения существующего поведения.
- Оценить полноту исходного набора, готовность группы A, зависимости, вопросы по изображениям и токенам, соответствие заданной схеме бустера.
- Подготовить **компактный отчёт по решениям**: группировка, план Java-вмешательств, карты D, вопросы к авторскому тексту, ожидаемые файлы выпуска, список блокеров. Подробные приложения — только там, где полезны.
- Не проводить повторно полную проверку уже созданных простых карт без оснований.

### Этап 5. Рассмотрение пользователем

- Пользователь утверждает, отклоняет или корректирует планы общих и индивидуальных реализаций и допустимые Java-изменения.
- Нет необходимости согласовывать каждую обычную карту A.
- Если на этапе реализации появляется принципиальное отклонение от одобренного плана, Codex сообщает о нём и не вносит такое изменение самовольно.

### Этап 6. Реализация, комплектование и минимально достаточная проверка

- Вносить **только согласованные** Java-патчи непосредственно в локальную рабочую копию Forge, не синхронизируя её с удалённым репозиторием. Сохранять возможность отката к локальной контрольной точке и не задевать посторонние изменения.
- После внедрения необходимых механизмов дописать скрипты B/C, создать необходимые токен-скрипты и другие поддерживаемые игровые объекты.
- Скачать доступные полноразмерные изображения карт и токенов, переименовать с учётом утверждённой схемы уникальных имён для Forge и подготовить их для ручной установки; создать файлы `editions` по выбранному формату.
- Сделать одну разумную массовую проверку загрузки/ссылок, адресные игровые тесты новых или рискованных механизмов и ограниченную проверку формируемых бустеров. **Не запускать исчерпывающие тесты каждой карты и повторные полные сборки без причины.**
- Оформить результат, список отсутствующих изображений и нерешённых карт, инструкцию ручной установки и краткий финальный отчёт.

## 7. Правила формирования кард-листов

**Три поддерживаемые формы:** классический драфтовый (пример: Core Set 2020), драфтовый с расширенными слотами (пример: Aetherdrift), недрафтовый (пример: The Exploration of Whisperwild). Выбор формы и состав бустера определяет пользователь. Файлы-примеры служат образцами синтаксиса, но не заменяют проверку актуального парсера Forge.

- Для драфтового: корректная `[metadata]`, `[cards]`, необходимые листы печати/секции и `Booster`/`BoosterSlots` по **заданной пользователем** схеме. Проверять, что указанные листы существуют, что реально набирается нужное число карт и что исключения не попадают в слоты ошибочно.
- Для недрафтового: регистрация карт с их настоящими редкостями, **без собственного `Booster`**. Не превращать редкие/мифические карты в особую категорию лишь потому, что выпуск недрафтовый.
- Использовать присвоенные уникальные имена Forge во всех строках `[cards]`, в том числе закомментированных; сверять их с `Name:` соответствующих скриптов и именами изображений.
- Сохранять номера карт и пробелы нумерации, если они заданы источником; если номеров нет — назначить стабильные без произвольной перенумерации при продолжении.
- **Нереализованные карты сохранять на своих позициях закомментированными строками в `[cards]`** (например, `# 103 R Card Name`). Отдельный список указывает, почему карта не реализована. Пользователь сможет вручную добавить скрипт и снять комментарий.
- Не путать полноту списка опубликованного выпуска с полнотой реализованных скриптов. Драфтовые слоты проверять по фактически доступным незакомментированным картам. При недостаточном пуле сообщить, что соответствующий бустер пока неработоспособен, а не подменять схему.
- Не дублировать механические скрипты ради альтернативных иллюстраций; специальные промо/варианты и токены учитывать по фактической структуре источника.

## 8. Сайты и изображения

**PlaneSculptors:** текстовые сведения выпуска обычно собраны на общей странице; представленные там картинки могут быть обрезанными. Требуется перейти по ссылке к полному изображению и скачать **его**, а не миниатюру. Ошибки отдельных ссылок, в том числе связанные с именами карт, не должны останавливать весь импорт.

**MTGNexus:** визуальный список может занимать несколько страниц; для полного текста и изображения нужно открывать страницу каждой карты. Не пропускать пагинацию и многочастные карты.

Codex вправе использовать доступный встроенный браузер, прямые запросы и другие разрешённые способы; выбирает наиболее надёжный и не повторяет неудачную попытку бесконечно. Проверяет тип и целостность скачанного файла. Не заменяет отсутствующую картинку произвольным артом и не генерирует изображения самостоятельно.

Отдельно формируются три списка недостающих изображений: **обычные карты**, **токены**, **эмблемы/прочие игровые изображения**. Токен-скрипт создаётся даже без изображения, если способность понятна. Пользователь самостоятельно восполняет недостающее.

## 9. Проверки, AI и уровень уверенности

- `DeckHas` означает реально предоставляемые возможности; `DeckHints` — полезные синергии; `DeckNeeds` — зависимости. Не классифицировать пожертвование или сброс оппонента как собственный источник ресурса. Для нескольких независимых возможностей `DeckHas` использовать проверенную семантику `&`, не заменять ею механически все `|` в любых полях.
- Учитывать особенности многочастных карт, общих Deck-полей, Skill, SVar и ссылок на токены. Использовать проверенные выводы DWAP, но сверять их с актуальным Forge.
- По умолчанию достаточно: проверка структуры/загрузки, проверка отсутствующих ссылок, сравнение ключевых характеристик и Oracle, несколько выборочных/рисковых игровых сценариев, проверка заданных бустерных слотов.
- Для нового Java-механизма проводить минимальные адресные регрессионные проверки, в том числе на риск изменения штатного поведения. При необходимости читать все зависимые классы; глубину определяет риск, а не жёсткий запрет.
- Отдельно различать: «загружается», «проверено адресным тестом», «не проверено в реальной партии», «частично реализовано/заблокировано». Не выдавать запуск тестов за доказательство правильной игры AI.

## 10. Постоянная база знаний и устаревание

Знания хранятся в небольших тематических справочниках навыка (`.agents/skills/forge-custom-set-builder/`): особенности скриптов, подсказок AI, устройства движка, проверенных кастомных механик, выпусков и источников. `SKILL.md` остаётся компактной инструкцией маршрутизации; подробности читаются **по потребности**.

Записывать лишь повторно полезные факты: назначение классов и цепочек, подтверждённые шаблоны, ограничения API, проверенные случаи, типичные ошибки. Отмечать источник/контекст проверки и статус: **проверено / требует актуализации / устарело / заменено**. Не изменять запись на основании одной необъяснённой ошибки.

**База знаний — не истина о текущем Forge.** Перед применением существенной старой реализации проверять необходимые классы, методы и операторы в текущем локальном коде; если обнаружены изменения — исследовать и обновлять только затронутые знания. Полный мониторинг апстрима и аудит пользовательских патчей ведутся **в другом проекте** и не входят в Builder.

Накопленные знания должны оставаться полезными после удаления временной рабочей папки и старых отчётов.

## 11. Временная папка, продолжение и результат

Пример изолированного каталога (путь можно выбрать в первом задании):

```text
D:\1\forge-builder\<CODE>\
  cards\                 скрипты карт
  tokens\                токен-скрипты
  editions\              файл(ы) выпуска
  images\                полные изображения карт, токенов, эмблем
  source\                временный снимок исходных данных
  reports\               сводный план, проблемы, результаты проверки
  progress.md            только при необходимости длительного продолжения
  INSTALL.md             инструкция ручного переноса
```

В пределах непрерывной сессии не навязывать постоянное ведение `progress.md`: Codex может использовать собственный контекст и файлы. При длительном перерыве или переносе работы в другую сессию сохранять **краткое состояние**: утверждённый код, источник, состав бустера, готовые/оставшиеся группы, согласованные патчи, незакрытые вопросы и следующий шаг. Не пересказывать туда сотни скриптов.

**Выход проекта:** готовые скрипты и токены, скачанные изображения, файл(ы) выпуска, соответствие исходных и присвоенных имён карт, инструкция ручной установки, списки отсутствующих ресурсов и карт без реализации, краткий отчёт. Необязательные журналы и HTML/JSON остаются временными; после проверки зависимости можно удалить или архивировать их. Никакие постоянные навыки не должны ссылаться на временные абсолютные пути как на обязательную часть работы.

## 12. Критерии завершения задачи

Работа завершена, если: (1) все опубликованные карты учтены; (2) каждая получила статус и, если возможна, рабочий скрипт; (3) нерешённые карты остаются закомментированными в кард-листе и перечислены отдельно; (4) заданная схема бустера реализована или невозможность честно обозначена; (5) изображения скачаны там, где доступны, а пропуски перечислены; (6) были выполнены необходимые, но не избыточные проверки; (7) Java менялась только по одобренным решениям; (8) файлы пригодны для ручного переноса, а временную папку можно очистить без потери постоянных знаний.

---

**Применение:** данная спецификация отражена в SKILL.md 1.0. Изменения Java и скриптов требуют отдельных заданий и разрешений, предусмотренных этапами.
