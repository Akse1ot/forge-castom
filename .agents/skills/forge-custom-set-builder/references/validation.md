# Проверка по риску, а не по количеству карт

**Минимум:** (1) полнота списка источника и связи ID → имя; (2) структура, ссылки SVar/TokenScript; (3) массовая загрузка обеих частей карт без подмены одноимённой картой из базы; (4) sanity-check требуемого бустера и незакомментированных карт; (5) несколько адресных игровых тестов **новых или рискованных** эффектов.

Не запускать проверку всех возможных игровых комбинаций и не писать отдельный тест для обычного Flying/Trample/типового ETB. Применять глубину по риску. Если менялся Java API, тестировать соответствующий путь и близкий штатный случай. Не делать повторную тяжёлую Maven-сборку ради косметики.

| Метка | Что действительно доказано |
|---|---|
| Imported | Исходная запись получена; не свидетельствует об игровом эффекте |
| Loaded | Скрипт читается и необходимые ссылки известны |
| Reviewed | Ключевые цели, условия, зоны, стоимость и Oracle сверены |
| Scenario-tested | Конкретные воспроизводимые игровые сценарии прошли |
| Gameplay-unverified | Не запускалась реальная партия; не означает ошибку |
| AI-unverified | Не проверялась практическая эффективность AI-подсказок |
| Blocked / partial | Скрипт не готов/точность неполная; должен оставаться закомментированным в editions |

Выбирай игровые сценарии прежде всего для нового engine hook, нестандартных триггеров, `may/up to`, затрат, смен зон, целей, multi-player, токенов, Aura/Equipment, Skills/Invoke и сложных комбинаций.

**Ловушки из DWAP:** `AbilityUtils.resolve` напрямую может обходить стек и перепроверку легальности цели; отсутствие ресурсов в подготовке теста может маскировать ошибку дополнительной стоимости. В тестах следует использовать нормальный путь игрового действия, если проверяется корректность целей/оплаты.

`BUILD SUCCESS` и `git diff --check` удостоверяют соответственно успешную сборку/формат diff, но **не** полноту поведения 300 карт и **не** качество AI.

При внешней рабочей папке проверки скриптов могут потребовать временно указать loader на папку либо использовать изолированную тестовую фикстуру. Не устанавливать staging-скрипты в игровые каталоги пользователя автоматически; если невозможно протестировать без установки — обозначить границу проверки и согласовать безопасный способ.

## Четыре переиспользуемых приёма из текущего теста DWAP

**Статус: проверено чтением 30.10.2026**, ветка/HEAD и ограничения рабочего дерева — `engine-notes.md`. Прочитан постоянный `forge-gui-desktop/src/test/java/forge/game/card/DWAPCardScriptTest.java` и определения helpers в `forge-gui-desktop/src/test/java/forge/ai/AITest.java`. Нового запуска тестов не было.

1. **Точный файл вместо поиска имени.** `load(Path, Player, ZoneType)` читает UTF-8, удаляет blank lines, вызывает `CardRules.fromScript`, `new PaperCard`, `CardFactory.getCard`, назначает новый game timestamp и кладёт объект в нужную зону. В будущем параметризовать staging-путь/код/редкость, не переносить DWAP/252/Rare как общие константы. Для smoke-check пройти `card.getStates()`, у triggers/replacements вызвать `ensureAbility()`, собрать ошибки через TestNG `SoftAssert`. Это загрузка, не исполнение всех эффектов.
2. **Матрица границ через TestNG DataProvider.** Несколько случаев «без/с ресурсом», «цель выбрана/не выбрана», «существо/planeswalker» вместо теста на каждую карту. Доступны `SpellAbility.canTarget`, `isTargetNumberValid`, `getMinTargets`, `getSubAbility`; проверять также отрицательные цели. `AITest` предоставляет `initAndCreateGame`, `initAndCreateThreePlayerGame`, `addCardToZone`, `addCard`, `addToken`; они используют полноценную инициализацию FModel, это не лёгкий unit harness.
3. **Изменение цели до разрешения.** В `snowslideResolvesWithOptionalOrDetachedEquipment` после выбора меняется attachment, затем `game.getStack().add(ability)` и `resolveStack()`. В `forge-game/.../zone/MagicStack.java` цепочка `resolveStack → hasFizzled` проверяет timestamp и `canTarget(card, true)`, удаляет нелегальные цели. Прямой `AbilityUtils.resolve` годится для эффекта с уже подготовленными входами, но не доказывает повторную проверку целей. Даже добавление в стек не доказывает оплату стоимости при разыгрывании.
4. **Доступность действия отдельно от результата эффекта.** `starHerdInvokeLimitPersistsAcrossTurnsButResetsForNewObject` проверяет `canPlay`, смену фазы, `addAbilityActivated`, `resetActivationsPerTurn`, затем настоящие `moveToGraveyard`/`moveToPlay`. `auroraStrixRequiresExactlyOneArtifactOrCreatureSacrifice` проверяет варианты `GameActionUtil.getAdditionalCostSpell` и `CostSacrifice` до/после появления ресурса. В `GameActionUtil` ветка `AlternateAdditionalCost` очищает исходные варианты и добавляет только копии с `canPlay()`. Эти проверки не симулируют UI и фактическую оплату; многопользовательские `unless` требуют отдельных случаев выбора/оплаты.

Исторические логи двух проходов подтверждают соответственно 18 и 17 успешных сценариев, а не 35 уникальных тестов и не все карты. Для будущего выпуска выбирать только нужные приёмы по риску; не копировать весь тест DWAP.
